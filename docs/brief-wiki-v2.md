# Задание: вики-функционал v2 (единое добавление, правки через модерацию, история изменений)

Этот файл — техзадание для ИИ-модели, выполняющей работу в репозитории. Прочитай его целиком, затем `docs/project-notes.md` (архитектура и журнал решений) и `docs/design-rules.md` (если уже существует). Выполняй **только ту задачу, которую тебе назвали** (номер ниже), не делай остальные «заодно».

## Контекст в трёх абзацах

Сайт памяти Т.И. Хитровой: статика (HTML/CSS/JS без сборки) на Cloudflare Workers, бэкенд — только Supabase (Postgres + RLS + Auth по коду на e-mail + Storage). Своего сервера нет: вся безопасность живёт в RLS-политиках базы, фронтенд им доверяет. Автодеплой: `git push` в `main` публикует сайт.

Три сущности контента: `events` (линия жизни, `index.html`), `people` (`people.html`, `person.html`), `articles` («Наследие», `nasledie.html`). У всех статус `unconfirmed → confirmed | rejected` (у статей ещё `draft`). Добавлять может любой залогиненный от своего имени; подтверждает модератор (`profiles.is_moderator`) на `moderation.html`.

Принятые владельцем решения (не обсуждаются, реализуются):
1. **Любая правка существующей записи идёт через модерацию**, так же как добавление. Автор не может править напрямую ничего, кроме своих черновиков статей (`status = 'draft'`, они не публичны).
2. **Полная история изменений** хранится для всех трёх сущностей и показывается списком «кто, когда, что». Диф «было/стало» по полям — не в этой версии.
3. Регистрация остаётся открытой для любого e-mail.
4. Дизайн — по `docs/design-rules.md` (Material Design 3 за основу, цвета и шрифты текущего сайта).

## Известная дыра, которую закрываем в первую очередь

Политика `people: любой залогиненный может редактировать` (создана в `supabase/migration_person_card.sql`) разрешает любому залогиненному `UPDATE` любой строки `people` без ограничений: можно выставить себе `status = 'confirmed'` в обход модерации и переписать чужую подтверждённую карточку. Её надо **удалить** (задача 1). После этого прямое редактирование в `person.html` перестанет работать — это ожидаемо, задача 3 переводит его на предложения правок.

## Целевая модель данных (задача 1)

Одна новая таблица `public.revisions` обслуживает и очередь правок, и историю:

```
revisions
  id              uuid pk default gen_random_uuid()
  entity_type     text not null check (entity_type in ('event','person','article'))
  entity_id       uuid not null
  kind            text not null check (kind in ('create','update','moderate'))
  patch           jsonb not null          -- для update: только изменённые поля {field: new_value}; для create: снимок записи; для moderate: {status: ..., note: ...}
  status          text not null default 'pending' check (status in ('pending','applied','rejected'))
  author_id       uuid not null references auth.users(id)
  author_name     text not null
  created_at      timestamptz not null default now()
  reviewed_by     uuid references auth.users(id)
  reviewed_by_name text
  reviewed_at     timestamptz
  moderator_note  text
  comment         text                    -- пояснение автора правки: «исправил год выпуска по диплому»
```

Правила:
- **Предложение правки** = строка `kind='update', status='pending'`, вставляет её любой залогиненный (`author_id = auth.uid()`). Сама запись в `people/events/articles` при этом не меняется.
- **Применение** делает только модератор через RPC-функцию `apply_revision(revision_id uuid)` (`security definer`, `set search_path = public`, внутри проверка `is_moderator()`): накладывает `patch` на строку сущности динамическим UPDATE по разрешённому списку полей (белый список на каждую сущность, `status`/`created_by`/`id` менять через patch нельзя), ставит `status='applied'`, `reviewed_*`. Аналогично `reject_revision(revision_id, note)`.
- **История** для `create` и `moderate` пишется триггерами `after insert / after update of status` на трёх таблицах (уже с `status='applied'`), чтобы фронтенд ничего не должен был помнить. Существующие поля `confirmed_by*`, `updated_by*` не трогать, они остаются для обратной совместимости.
- **RLS на `revisions`:** insert — залогиненный от своего имени; select — модератор всё, автор свои; update/delete — никому (только через RPC).
- **RLS на `people`:** удалить политику `people: любой залогиненный может редактировать`. Оставить insert для залогиненного и update для модератора. Проверить, что у `events` и `articles` аналогично: update только модератор (+ у `articles` автор своих `draft/unconfirmed/rejected`, это оставить).

Миграция — один файл `supabase/migration_revisions.sql`, идемпотентный (`if not exists`, `drop policy if exists`, `create or replace function`). **Не применяй миграцию сам** и не запрашивай ключи: положи файл и напиши в отчёте «миграция готова к применению». Применяет владелец (через Claude с MCP-доступом к Supabase или SQL Editor).

## Задачи

Порядок — волнами: сначала грубый проход по всему, потом полировка. Каждая задача = одна сессия модели = один коммит (или несколько мелких), с отчётом в конце: что сделано, что не сделано, как проверить руками.

### Задача 0. `docs/design-rules.md` — дизайн-правила для всех следующих задач
Одна страница, не больше ~150 строк. На основе Material Design 3, адаптировано под текущий `style.css` (взять оттуда реальные цвета, шрифты, радиусы, не выдумывать новые). Обязательные разделы: шкала отступов (4/8/12/16/24/32), типографика (3–4 размера, не больше), цвета с ролями (фон, поверхность, текст, акцент, предупреждение, ошибка, «подтверждено»), кнопки (primary/secondary/text + состояния hover/active/disabled/loading), поля форм (label сверху, ошибка под полем, обязательные помечены), модалка/лист (десктоп: центр, max-width 720; телефон < 600px: полноэкранный лист снизу, кнопка закрыть сверху, primary-кнопка прижата к низу), чипы-фильтры, бейджи статусов, тултип/поповер, минимальная область нажатия 44px, фокус видимый с клавиатуры. В конце — чек-лист «перед коммитом проверь» из 8–10 пунктов. Существующий UI не переделывать в этой задаче.

### Задача 1. Миграция `supabase/migration_revisions.sql`
Ровно то, что описано в «Целевая модель данных». Плюс RPC `submit_revision(entity_type, entity_id, patch, comment)` не нужна — вставка напрямую через RLS. В отчёте — список всех политик на 4 таблицах после миграции.

### Задача 2. Единая кнопка «+ Добавить» (волна 1, черновая)
- В шапке (`app.js`, `initHeader`) одна кнопка «+ Добавить» для залогиненных; для гостей — та же кнопка открывает вход.
- Поп-ап по `docs/design-rules.md`: три таба **Событие · Человек · Материал**. Открывается с табом, соответствующим текущей странице (`index` → Событие, `people/person` → Человек, `nasledie` → Материал).
- Переиспользовать существующие формы добавления события и человека из `app.js` (не дублировать логику вставки, вынести в функции). Таб «Материал»: только заголовок + категория (от Т.И. / от коллег) + тип; по кнопке «Продолжить в редакторе» создаётся черновик статьи и открывается `nasledie.html#edit/:id`.
- После отправки: короткое подтверждение «Отправлено на проверку», поп-ап закрывается, счётчик модерации обновляется.
- Старые точки входа добавления (кнопка на `people.html`, «+ Написать» на `nasledie.html`) заменить вызовом того же поп-апа с нужным табом.
- Волна 1 = всё работает, но без вылизывания. Не тратить время на анимации.

### Задача 3. Правки через предложения (волна 1)
- `person.html`: форма редактирования вместо прямого `update` собирает диф (только изменённые поля) и вставляет строку в `revisions` с `kind='update'`, поле «Комментарий к правке» (необязательное). После отправки показать плашку «Правка отправлена на проверку». Если у записи есть pending-правки текущего пользователя — показать это на карточке.
- События: добавить в попап события (index.html) кнопку «Предложить правку» для залогиненных с тем же механизмом (форма из тех же полей, что при добавлении).
- Статьи: подтверждённую статью тоже можно «Предложить правку»: открывается редактор в режиме предложения, сохраняет патч `{title, content, ...}` в `revisions`, не трогая статью.
- `moderation.html`: новая секция «Правки» с карточками pending-ревизий: сущность, ссылка на неё, автор, дата, список изменённых полей «поле: новое значение» (старое значение подгружать из текущей записи и показывать рядом), кнопки «Применить» (`rpc apply_revision`) и «Отклонить» с заметкой. Счётчик в шапке учитывает pending-ревизии.

### Задача 4. Универсальная иконка метаданных (волна 1)
- Один компонент в `app.js`: `renderMetaIcon(entity_type, entity_id, row)` → маленькая нейтральная иконка (ⓘ или «часы»), 44px область нажатия. По клику/наведению — поповер по `design-rules.md`:
  - строка 1: «Добавил(а) Имя · дата»
  - строка 2: «Проверил(а) Имя · дата» (или «На проверке»)
  - строка 3: «Источник: …» если есть (ссылки кликабельны)
  - далее «История» — список из `revisions` (status applied/rejected), по строке на запись: «дата · Имя · изменил: поле1, поле2 · комментарий». Загружать лениво при открытии поповера.
- Поставить иконку: на карточке человека (`person.html`, **заменить** текущее полотно «кто добавил / кто редактировал»), в попапе события на таймлайне, в режиме чтения статьи, на карточках в очереди модерации.
- Гостю показывать всё, кроме e-mail (e-mail нигде не выводить).

### Задача 5. Волна 2 — полировка по `design-rules.md`
Пройти по всем экранам задач 2–4 и привести к правилам: отступы, состояния кнопок, ошибки валидации под полями, поведение на iPhone 12 mini (375×812) без горизонтального скролла, фокус с клавиатуры, тексты кнопок глаголами. Ничего нового не добавлять.

Плюс две правки по итогам аудита сайта (2026-09-14):
- **Мобильная шапка (все страницы, ширина < 600px).** Сейчас пункты меню обрезаются справа («НАСЛЕДИ…»), и одновременно под меню показан бургер. Оставить один механизм: на телефоне только бургер с выпадающим списком разделов (Линия жизни / Люди / Наследие) плюс кнопка «+ Добавить» и вход; горизонтальный список пунктов на телефоне скрыть. Проверить на 375px: ничего не обрезано, нет горизонтального скролла.
- **Пустое «Наследие» (`nasledie.html`).** При нуле подтверждённых материалов не показывать две пустые секции с заглушками. Показывать один блок-приглашение: короткий текст («Здесь будут статьи и интервью Татьяны Ивановны, а также воспоминания учеников и коллег. Станьте первым.») и кнопку «+ Добавить». Чипы-фильтры и заголовки секций появляются, как только есть хотя бы один материал. Если материалы есть только в одной секции — показывать только её, без пустой второй.

- Не трогать: `wrangler.toml`, `.assetsignore`, `supabase/schema.sql`, уже применённые миграции. Новые миграции — только новыми файлами.
- Не добавлять сборщики, фреймворки и npm-зависимости. Библиотеки только как сейчас: `<script src>` с CDN, версия закреплена.
- Все пользовательские строки по-русски, обращение к пользователю на «вы».
- Никаких ключей и токенов в коде и в отчётах. Anon-ключ Supabase уже есть в `app.js`, других не нужно.
- Перед коммитом: `git status`, коммитить только свои файлы, осмысленное сообщение по-русски («Единая кнопка добавления: поп-ап с тремя табами»).
- В конце сессии дописать 3–5 строк в `docs/project-notes.md`, раздел «Журнал», с сегодняшней датой: что сделано, что осталось, как проверить.
- Если что-то из задания невозможно или противоречит коду — не изобретать обход, остановиться и написать вопрос в отчёте.
