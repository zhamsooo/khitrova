## Видение (родилось 2026-09-01) — большая версия, НЕ на этой неделе

Идея: граф-таймлайн как ядро сайта, вики-контент вокруг него. Перекликается с методом ТИ («линия и точка») — приятная пасхалка для учеников.

**v1 — Граф-таймлайн (ядро)**
- Главная — динамический граф в духе Obsidian
- Горизонтальная линия жизни ТИ, скроллится по горизонтали
- Ключевые вехи: рождение, школа, муз. училище, консерватория, преподавание, гастроли
- Слой «ученики» — вкл/выкл (за годы преподавания — очень много выпускников, разного уровня известности)
- Требование: минимализм, лёгкость, без глюков, быстрая загрузка на телефоне

**v2 — Вики-контент**
- Любой ученик может добавить воспоминание, статью, фото/видео/аудио
- Может предложить правку графа (добавить себя, однокурсников)
- Модерация: статус «неподтверждено» → «подтверждено» (галочка), попап при наведении — кто подтвердил, источник (например, фото афиши)
- Нужны роли: обычный пользователь / модератор

**v3 — Люди на фото + комментарии**
- Отметка людей на фото, тоже через вики (один загрузил, другой отметил)
- Комментарии под фото и статьями
- Нужна минимальная регистрация — пока не продумано, как именно

**Открытый вопрос:** v1–v3 по сложности — это отдельный полноценный продукт (граф-визуализация + вики + модерация + аккаунты), сопоставимый по объёму с [[Нарезалка партитур]], а не «сайт за 2 вечера». ### Стек для прототипа графа (набросок 2026-09-01)

- **Первый вариант (реализован):** узлы вех фиксируются по X согласно возрасту (timeline), Y — свободный, вычисляется силовой симуляцией (D3.js/d3-force на SVG), чтобы узлы не наслаивались. Даёт эффект «графа», который одновременно читается как таймлайн. Прототип с плейсхолдер-данными — см. `Проекты/Сайт памяти — прототип/index.html`.
- **Найденная альтернатива — [TimelineJS3](https://github.com/NUKnightLab/TimelineJS3) (Knight Lab):** открытый код, лицензия MPL-2.0 (можно самостоятельно хостить и модифицировать законно). Даёт из коробки: полированный UI, фото/видео/аудио в событиях, мобильную оптимизацию, проверено годами. Есть поле `group` — события можно разложить по дорожкам (например «Вехи жизни» / «Ученики»), но переключателя вкл/выкл дорожки из коробки нет — добавляется лёгкой JS-обёрткой (пересоздать Timeline с отфильтрованным JSON по клику), без форка ядра.
  - Плюс: на порядок меньше работы, сразу качественно и стабильно, хорошо подходит под вики-контент (фото/видео в событии)
  - Минус: теряется собственно «граф в духе Obsidian» — это линейная слайд-таймлайн, не узловая сеть. Пасхалка «точка = развёрнутая линия» всё равно работает: точка на линии кликом разворачивается в карточку.
  - **Решение пока не принято** — сравнить оба варианта визуально, выбрать один.
- **Сайт целиком (позже, v1+):** статическая генерация (Astro) — вики-контент и биография рендерятся в HTML, граф/таймлайн — единственный интерактивный «остров» JS. Быстро грузится, хорошо на телефоне.

### Граф учеников — отдельная задача от линии жизни (набросок 2026-09-02)

Раздел «Ученики» — не список и не тот же самый граф-таймлайн, а отдельная визуализация: сеть людей, а не линия времени. TimelineJS сюда не подходит (он только про хронологию), нужна отдельная библиотека под графы/сети.

**Кандидаты (сравнить визуально, решение не принято):**
- **[Cytoscape.js](https://js.cytoscape.org/)** (MIT, ~300 КБ) — специализированная библиотека под графы, готовые layout'ы (`cose` органическая кластеризация, `concentric` кольцами, `breadthfirst` иерархия), тач-жесты и пинч-зум из коробки, **compound nodes** — узлы можно группировать в подписанные контейнеры и переключать группировку сменой поля `parent`. Рекомендация по умолчанию — ниже больше кода из коробки, порог входа ниже, чем у голого D3.
- **[Sigma.js](https://www.sigmajs.org/)** — рендер через WebGL, тянет тысячи узлов без просадки. Избыточно для текущего масштаба (десятки-сотни учеников), но запасной вариант, если граф вырастет (например, если добавить связи между самими учениками, не только с ТИ).
- Голый D3-force (уже опробован в `index.html` этой папки) — полный контроль над визуалом, но кластеризацию/зум/тач писать руками.

**Идея группировки — не статичная, а переключаемая (2 линзы на одних и тех же людях):**
1. **Однокурсники** — по году поступления/выпуска. Данные уже есть в схеме: `study_start`/`study_end` на каждой записи `people`, ничего дополнительно собирать не нужно.
2. **По художественному руководителю хора / главному хормейстеру в период учёбы** — обучение длилось 5 лет, за это время мог смениться худрук, и разные ученики застали разных руководителей. Это отдельное маленькое множество данных, которого пока нет: список тенур руководителей (кто, с какого по какой год) — по структуре ровно как эры на линии жизни ТИ. Связь ученик↔руководитель **не хранится вручную**, а считается на лету пересечением дат (`study_start`–`study_end` ученика с периодом пребывания руководителя в должности) — один человек может попасть под двух руководителей, если застал смену.

Переключатель «однокурсники ⇄ по худруку» над одним и тем же набором узлов — с compound nodes в Cytoscape.js это буквально смена `parent` у узлов + релэйаут, эффект «граф на глазах перестраивается в другие кластеры». Существенно интереснее плоского списка учеников и напрямую использует уже собранную модель данных.

**Что нужно донабрать:** список худруков/главных хормейстеров хора с годами тенуры (пока не собрано, отдельная задача от вечера 1).

**Переименование раздела (уточнение 2026-09-02): «Ученики» → «Люди».** Точнее описывает содержимое — не только ученики, но и коллеги, другие артисты, все, с кем ТИ пересекалась. Совпадает с уже заложенным в схему полем `people.relation_type` (ученик/коллега/другое/сама ТИ) — фильтр по типу связи ложится прямо на существующие данные, ничего доп. моделировать не нужно.

**Живые референсы именно под фильтруемый граф людей «на лету» (найдено 2026-09-02):**
- **[Six Degrees of Francis Bacon](https://www.sixdegreesoffrancisbacon.com/)** (Carnegie Mellon, ~14 000 персон, ~200 000 связей) — граф исторических персон с фильтрами по категориям/профессиям («Дипломаты», «Судьи», «Историки»...) кнопками внизу экрана; пан/зум, тултип при наведении на связь, клик — детали отношения. Прямой прецедент под фильтр по `relation_type`.
- **[Histograph](https://www.histograph.org/)** — граф людей/мест/событий с поиском, фильтром по типу и **слайдером по времени** («slide across time») — хорошая модель для добавления декадного фильтра поверх фильтра по типу связи.
- Уже отмеченный ранее **[Kindred Britain](https://kindred.stanford.edu/)** — тоже подходит как референс интерфейса фильтров у графа людей, не только у таймлайна.

### Раздел с текстами — «Наследие», одна сущность с фильтрами, не отдельные страницы (уточнение 2026-09-02)

Изначально рассматривалось два варианта: (а) отдельная страница «Наследие» только под тексты самой ТИ + общий раздел под тексты учеников, (б) одна сущность на всё. Решение — **(б), одна сущность**: собственных текстов и интервью ТИ немного, отдельная страница под них будет казаться пустой. Тексты учеников (воспоминания, статьи) и тексты самой ТИ живут в одном разделе, различаются фильтром, а не структурой страниц.

**Название раздела: «Наследие».** Точнее «Статей»/«Публикаций»/«Воспоминаний» (прежние варианты) — покрывает и то, что ТИ создала сама, и то, что она оставила в учениках. Не пересекается по смыслу с общим брендом сайта («Сайт памяти» — не дублируем слово «память» внутри памяти).

**Фильтры внутри раздела:** «От Т.И.» / «От учеников» (соответствует `articles.author_person_id` — своя запись ТИ в `people` с `relation_type` = сама ТИ, отличима от учеников/коллег), плюс по типу (статья / интервью / воспоминание).

### Инструменты по трём разделам сайта — сводка (уточнение 2026-09-02)

Библиотека vs фреймворк: библиотека — узкий инструмент под одну задачу, вызывается из кода страницы (TimelineJS: «нарисуй таймлайн из этих данных»); фреймворк — структура, в которой живёт весь сайт целиком (Astro). Библиотеки подключаются внутрь фреймворка как виджеты.

| Раздел | Инструмент | Тип |
|---|---|---|
| Линия жизни | TimelineJS3 | библиотека — визуализация таймлайна |
| Люди | — (обычная вёрстка: колонки + карточки-кружки) | нет, задача не требует спец. библиотеки — см. ниже |
| Наследие | — (обычная вёрстка: карточки + фильтр-чипы) | нет, задача не требует спец. библиотеки |
| Наследие → форма ввода | Tiptap | библиотека — WYSIWYG-редактор текста |
| Наследие → безопасность | DOMPurify | библиотека — санитизация пользовательского HTML |
| Весь сайт | Astro | фреймворк — статическая генерация, держит все разделы вместе |

«Наследие» не получило отдельной визуализационной библиотеки не по недосмотру — «список карточек с фильтрами» не сложнее готового решения, у него просто нет той сложности (рисование таймлайна/графа руками), ради которой нужны TimelineJS/Cytoscape.

**«Люди» — пересмотрено 2026-09-02, Cytoscape.js снят с раздела.** Собрали рабочий прототип на Cytoscape.js (граф, компаунд-группы, переключение группировки), но по факту у людей не было ребёр — только общий узел-хаб «ТИ», к которому тянулась линия от каждого. Это тавтология (все на странице и так связаны с ТИ, иначе их бы тут не было), а не полезная связь, и после того как хаб убрали, ничего графового не осталось — просто люди, разложенные по категориям (десятилетие/эпоха/тип связи). Это задача про сетку карточек, не про граф, и Cytoscape (canvas + физический движок) тут был явно тяжелее задачи. Переделали на обычную HTML/CSS-раскладку: те же колонки в хронологическом порядке, те же фильтры и поиск, без библиотеки — легче, доступнее (Cmd+F, читалки экрана), кликабельные карточки вместо canvas-хиттестинга.

**Когда граф всё же будет оправдан:** если появятся настоящие связи между самими людьми (не только с ТИ) — например, «выступали вместе на одном концерте», «переписывались», «муж и жена среди учеников». Тогда рёбра покажут то, что список не может. Сейчас таких данных нет. Cytoscape.js и Sigma.js остаются в кандидатах на этот случай (см. выше), просто не для текущей версии раздела «Люди».

### Бэкенд / модель данных (набросок 2026-09-01)

Владелец предложил 4 сущности (биография-таймлайн, статьи, ученики, медиа). Разбор + 3 поправки к модели:

1. **«Ученики» → «Люди» (people).** Одна и та же персона может быть и учеником на таймлайне, и автором статьи, и коллегой, и человеком, отмеченным на фото. Если сделать отдельную таблицу «ученики», придётся дублировать карточку человека под каждую роль. Лучше одна таблица `people` с полем `relation_type` (ученик / коллега / другое / сама ТИ).
2. **Личность ≠ аккаунт.** Подавляющее большинство людей в `people` никогда не зарегистрируются (их впишут другие). Авторизация — отдельная таблица `users`, у которой есть необязательная ссылка на `people` (когда человек «заявляет права» на свою карточку).
3. **Статьи — строки в БД, не файлы.** Раз контент приходит от разных людей через веб-форму (а не через git), markdown-текст статьи логичнее хранить полем в БД (queryable: статус модерации, автор, дата), а не папкой .md-файлов на диске. Рендерить в HTML при показе.
4. **Модерация — не отдельная система, а повторяющиеся колонки.** На каждой модерируемой сущности (событие, статья, привязка человека к фото) — одинаковый паттерн полей: `status` (unconfirmed/confirmed), `confirmed_by` (кто подтвердил), `source` (ссылка/книга/фото афиши). Общий движок модерации — избыточно для такого масштаба.
5. **«Кто загрузил» — всегда виден, обязателен; источник — виден когда есть, но опционален (уточнено 2026-09-13, финальная формулировка после отката).** Автор (`created_by_name`) гарантирован автоматически самой природой системы — без авторизации ничего добавить нельзя, поэтому у поля даже не встаёт вопрос «обязательное или нет». Источник (`source`) — другое дело: часто его просто не существует (личное воспоминание, устный рассказ), требовать его для каждого факта значило бы отсекать честные, но неподтверждаемые документом воспоминания. Поэтому `source` остаётся необязательным полем в форме и в БД (nullable) — **но когда он есть, он обязательно показывается** в попапе рядом с автором (уже реализовано, см. `index.html` `showBadgeTip`). Правило — про видимость, а не про принуждение к заполнению. (Была попытка сделать `source` NOT NULL тем же днём — откатили в тот же день, коммит `a810524`, как раз по этой причине.)
6. **Поправка к схеме (уточнение 2026-09-13) — 7-табличный дизайн ниже не реализован, кроме `profiles`+`events`.** В реальной Supabase-базе физически существуют только `public.profiles` и `public.events` (см. `supabase/schema.sql` и `supabase/migration_moderation.sql` в репозитории). Таблицы `people`, `articles`, `media`, `media_people`, `comments` из чернового дизайна 2026-09-01 (ниже) — это ещё не воплощённая архитектура, а зафиксированная идея на будущее (нужны для v2 «вики + люди + наследие»). Также в `events` поля модерации называются не `confirmed_by`, а `moderated_by`/`moderated_by_name`/`moderated_at`/`moderator_note` (переименовано в ходе миграции — см. журнал 2026-09-03). Не путать черновую схему ниже с фактическим состоянием базы.

**Черновая схема (7 таблиц):**

```
people            id, фио, relation_type, institution (null, только если ученик),
                  study_start, study_end (null), notes (свободный текст про запас),
                  user_id (FK users, null), status, confirmed_by, source

users             id, email, role (обычный/модератор/админ), person_id (FK people, null)

events            id, date, date_precision (точная/год/примерно), on_timeline (bool),
                  title, description, status, confirmed_by, source

articles          id, title, content_md, author_person_id (FK people, null),
                  author_label (текст — если автор не в people, напр. внешняя перепечатка),
                  status, confirmed_by, source

media             id, type (photo/video/audio), storage_key, caption,
                  linked_entity_type, linked_entity_id, uploaded_by (FK users),
                  status, confirmed_by, source

media_people      media_id, person_id, tagged_by (FK users), status, confirmed_by

comments          id, entity_type, entity_id, author_id (FK users), text, created_at
```

**Уточнение 2026-09-01 — `timeline_events` → `events` (одна таблица, не две):** событий вообще (концерт, вечер памяти) больше, чем событий-вех на таймлайне жизни ТИ. Не заводим вторую таблицу, а добавляем в `events` флаг `on_timeline` — веха таймлайна это просто событие с `on_timeline=true`. Событие вроде концерта памяти 2026 года (уже после смерти ТИ, не веха её жизни) хранится там же с `on_timeline=false` и показывается в других разделах сайта (например «Новости» / «Память»), не на линии жизни. `comments` уже универсальна (`entity_type`/`entity_id`) — подходит и для медиа, и для статей, и для событий без отдельной таблицы под каждый тип.

**Хранилище и стек:**
- Для аккаунтов + БД + файлового хранилища медиа — рассмотреть один сервис вместо трёх (Supabase: Postgres + Auth + Storage в одном, щедрый бесплатный тариф, open source — не запирает). Экономит много бэкенд-работы для соло-разработки.
- Медиа-бинарники — в объектное хранилище (Supabase Storage или Cloudflare R2), в БД — только `storage_key`/URL и метаданные.
- Решение по стеку хранения — не сейчас, актуально к v2 (вики+модерация), не к v0 этой недели.

**Хранилище медиа и уровни доступа (уточнение 2026-09-01):**
- **Решение: IDrive e2.** Фиксированный тариф 1 ТБ — $15 первый год (акция -50%), далее $30/год; встроен 3× бесплатный egress (скачивание бесплатно, пока не превышает тройной объём хранимого). Для камерного трафика сайта памяти этого с большим запасом хватит. Полноценно S3-совместим — архитектурно ничего не меняется, значение просто идёт в поле `storage_key`, схема (публичный/приватный бакет, подписанные ссылки) работает как описано ниже.
- **Cloudflare R2 — отклонён по цене (уточнение 2026-09-01):** ~$180/год за 1 ТБ хранения (egress при этом бесплатен без потолка) — против $15–30/год у IDrive e2. R2 имел бы смысл только при трафике, стабильно выходящем за 3× бесплатного egress IDrive e2 — маловероятно для этого проекта.
- **IDrive e2 сам по себе — не CDN, нужен CDN-слой поверх (уточнение 2026-09-01).** S3-совместимое хранилище (как и R2, как и любой S3) физически лежит в одном регионе — «быстро всем клиентам независимо от локации» само по себе не даёт. Для этого бакет нужно посадить за CDN: подключить кастомный домен и проксировать через Cloudflare (бесплатно, IDrive e2 это позволяет как любой S3-совместимый бакет с публичным доступом) — тогда файлы кэшируются на точках Cloudflare по всему миру, а не отдаются каждый раз с одного сервера IDrive. Разница с Cloudflare R2: у R2 эта интеграция нативная (тот же вендор, что и Pages/CDN — один клик), у IDrive e2 — ручная настройка CNAME + прокси, но результат тот же и тоже бесплатный.
- **pCloud — не подходит для этой задачи.** Это потребительский сервис синхронизации файлов (как Dropbox), не объектное хранилище для веб-приложений: API не S3-совместим (нельзя переиспользовать готовые SDK и паттерн подписанных ссылок — придётся писать интеграцию с нуля под их конкретный API), нет встроенной привязки прав доступа к ролям пользователей сайта, и по духу это продукт для личного бэкапа, а не для раздачи контента от множества чужих людей публично. Экономии тоже не даёт — IDrive e2 дешевле и создан именно под такую задачу.
- **Уровни доступа** — поле `visibility` на `media` (и опционально на `articles`): `public` / `только ученики` / `только модераторы`. Технически — два бакета: публичный (прямые URL, кэшируется CDN, быстро) и приватный (доступ только по временной подписанной ссылке, которую сервер выдаёт, только если запрашивающий залогинен и подходит по роли — так же работают ограниченные файлы в Google Drive).
- **Веб-просмотрщик галереи** — да, легко добавляется отдельно от хранилища, в любой момент. Для фото — библиотека вроде PhotoSwipe (открытый код, лайтбокс, под телефон). Для мобильной производительности стоит генерировать несколько размеров превью при загрузке фото (не отдавать в галерею полноразмерный оригинал) — например через Cloudflare Images или простую resize-функцию на бэкенде.
- **Рекомендация по просмотрщику (уточнение 2026-09-01):** сам просмотрщик прав доступа не знает и не должен — он просто рендерит то, что ему передал бэкенд (публичную ссылку или временную подписанную, в зависимости от роли смотрящего и поля `visibility`), логика доступа целиком на сервере, как описано выше.
  - **Фото:** [PhotoSwipe](https://photoswipe.com/) (MIT, ~15 КБ, из коробки под тач/мобильные жесты) — лайтбокс с сеткой превью.
  - **Видео/аудио:** отдельная лёгкая библиотека не нужна — нативные `<video>`/`<audio>` в простом модальном окне достаточно для этого масштаба, не усложняет стек ради редких файлов.

**Форматирование статей (уточнение 2026-09-01):** `content` — просто текстовое поле в БД, форматирование (заголовки/жирный/курсив/цитата) кодируется прямо в тексте — либо markdown-синтаксис, либо HTML. Т.к. авторы статей — не разработчики, а музыканты, лучше не заставлять их писать markdown вручную, а поставить WYSIWYG-редактор (например Tiptap) поверх поля — он сам генерирует HTML при сохранении. **Важно:** пользовательский HTML обязательно санитизировать перед сохранением/показом (например DOMPurify), иначе это дыра для вставки вредоносного скрипта через форму статьи.

**Статья-строка vs файл, медиа-ссылка vs файл (уточнение 2026-09-01):** это стандартный паттерн, а не компромисс — текст/метаданные в БД (queryable, легко бэкапить), бинарники медиа только в объектном хранилище, в БД лежит лишь `storage_key`/ссылка на файл. Так устроены WordPress, Notion, Instagram — БД никогда не хранит сами байты фото/видео напрямую.

**Supabase — открытость и self-host (уточнение 2026-09-01):** да, полностью открытый код (Apache 2.0), весь стек (Postgres/Auth/Storage/Realtime) можно поднять самому через Docker Compose на своём сервере — тогда данные реально твои, без подписки на Supabase. Но: (1) свой сервер всё равно нужно арендовать (VPS, ~4–8 ГБ RAM для прод) — это не бесплатно, просто плата за инфраструктуру, а не подписка Supabase; (2) при self-host на себе — бэкапы, обновления, восстановление после сбоя. Managed-облако Supabase (supabase.com) — бесплатный тариф есть, но это подписочный SaaS с данными на их инфраструктуре. Решение self-host vs cloud — тоже не к этой неделе.

### Производительность и хостинг (уточнение 2026-09-01)

Проверил kapellanin.ru (пример медленного сайта от владельца) через сеть-панель браузера: TTFB 1748мс, полная загрузка 3.2с, 62 запроса на страницу (много мелких декоративных gif + фото по одному запросу + сторонний VK-виджет). Диагноз: сервер генерирует страницу динамически на каждый визит, без кэша — при параллельных посетителях это и есть узкое место, не пропускная способность канала.

**Вывод для нашего плана:**
- Задержка от географии (посетитель в другой части света vs сервер в Дании) — вопрос не пропускной способности («гб канал» не помогает), а физики расстояния/маршрута. Решается CDN — раздачей с точки, близкой к посетителю, а не с одного сервера.
- Astro отдаёт готовый статичный HTML — не требует пересчёта на сервере при каждом визите, в отличие от kapellanin.ru
- Сайт стоит хостить не на своём сервере в Дании, а на Cloudflare Pages / Netlify / Vercel (бесплатно, сами являются CDN с точками по миру), медиа — за CDN на R2/IDrive e2, БД/Auth — Supabase (управляемый сервис)
- При такой схеме 20–80 одновременных посетителей — тривиальная нагрузка, свой сервер для раздачи сайта не нужен
- **Cloudflare Pages + TimelineJS3 (уточнение 2026-09-01):** совместимы без оговорок. TimelineJS3 — это просто JS/CSS-библиотека + JSON с данными, никакого сервера ей не нужно, а Pages отдаёт любые статические файлы. Технических препятствий нет, вопрос выбора графа vs TimelineJS3 остаётся дизайнерским (см. «Стек для прототипа графа» выше), не хостинговым.

**Сравнение бесплатных тарифов (проверено 2026-09-01):**
- **Cloudflare Pages — выбор:** статический трафик и запросы не ограничены вообще (на любом тарифе), лимит только 500 сборок/мес
- **Netlify — не подходит:** с сентября 2025 новые аккаунты на системе кредитов, 300 кредитов/мес, трафик 20 кредитов/ГБ ≈ **~15 ГБ/мес** — при превышении сайт отключается до начала следующего месяца без предупреждения. Для медиатяжёлого сайта с непредсказуемыми всплесками — риск, что ляжет в неподходящий момент
- **Vercel (Hobby) — не подходит:** 100 ГБ/мес, аналогично жёстко отключается при превышении, доплатить нельзя. Плюс запрет на любое коммерческое использование, включая приём донатов на сайте — если захотим когда-то принимать пожертвования на поддержку сайта, это будет нарушением условий

    alter table public.events add column if not exists confirmed_by uuid references auth.users(id);
    alter table public.events add column if not exists confirmed_by_name text;
    alter table public.events add column if not exists confirmed_at timestamptz;
    alter table public.events add column if not exists verification_hidden boolean not null default false;
    grant update on public.events to authenticated;
    create policy "events: модератор может подтверждать" on public.events
      for update using (exists (select 1 from public.profiles where id = auth.uid() and is_moderator = true));
