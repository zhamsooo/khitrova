# Задание v5: вики-функционал — вход, форма человека, черновики, роль администратора, уведомления

Техзадание для ИИ-модели в репозитории. Прочитай целиком, затем `docs/design-rules.md`. Контекст — `docs/project-notes.md`, разделы «Принципы сайта» и «Журнал» за 2026-09-14. Выполнять **после** брифа v4 (`docs/brief-front-v4.md`) или параллельно, но не одновременно с задачей, трогающей те же файлы (F2/F4 и W2 оба правят форму человека в `app.js` — делать по очереди). Выполняй **только названную задачу** (W1–W5).

## Принципы сайта (от владельца, 2026-09-14) — проверяй каждое решение на них
1. **Устойчивость и простота.** Никаких хрупких конструкций, которые потребуют поддержки: минимум зависимостей, стандартные компоненты, понятные ошибки. Если можно сделать проще — делай проще.
2. **Наполнение только через вики.** Любой залогиненный добавляет, модератор проверяет и публикует. Владелец пользуется той же формой, что и все. Форма должна быть удобной и не ломаться.
3. **Любой экран.** ПК, телефон, планшет — сайт работает и читается везде.

## W1. Вход: код из 6 цифр, Enter работает
1. Длина кода — настройка Supabase (Authentication → Sign In / Providers → Email → «Email OTP Length»), не код сайта. Владелец ставит 6. На фронте (`app.js`, `MODALS_HTML` → `authOverlay`): все тексты «8 цифр» → «6 цифр», `maxlength="6"`, placeholder `123456`, `autocomplete="one-time-code"`.
2. Шаги входа обернуть в `<form>` (по одной на шаг `stepEmail`, `stepCode`, `stepProfile`) с `submit`-обработчиком, вызывающим ту же функцию, что и кнопка; `e.preventDefault()`. Enter в поле почты отправляет код, Enter в поле кода — проверяет, Enter в профиле — сохраняет. Кнопка в верхнем баре мобильного диалога (`btnAuthBarAction`) продолжает работать.
3. После ввода 6-й цифры — автоматически отправлять проверку (не ждать Enter/кнопки).
Критерий: вход с клавиатуры без мыши на десктопе; на телефоне клавиатура цифровая; неверный код — ошибка под полем, поле не очищается.

## W2. Форма человека: фамилия/имя/отчество, годы начала учёбы, должность коллеги
1. **Миграция** `supabase/migration_wiki_v5.sql` (идемпотентная, не применять самому):
   - `people`: `last_name text`, `first_name text`, `patronymic text`. `full_name` остаётся (обязательное, по нему поиск, старые записи «Волкова Е.» живут как есть).
   - Триггер `before insert or update` на `people`: если `last_name` не пуст — `full_name := trim(concat_ws(' ', last_name, first_name, patronymic))`. Значит, фронт может присылать только части, а старые записи без частей не трогаются.
   - `apply_revision`: в ветку `person` добавить три поля (скопировать функцию целиком из последней миграции, где она определена — `migration_front_v4.sql`, если уже есть, иначе `migration_revisions.sql`).
2. **Единый диалог добавления, таб «Человек»** (`app.js`): вместо одного поля «Имя Фамилия» — три outlined-поля в ряд на десктопе / столбиком на телефоне: «Фамилия» (обязательное), «Имя» (обязательное), «Отчество» (необязательное, supporting text «Если известно»). Вставка отправляет `last_name/first_name/patronymic`; `full_name` собирает триггер (но на клиенте тоже собрать и отправить, чтобы `not null` не сработал раньше триггера — триггер перезапишет тем же значением).
3. **Годы учёбы**: у каждого учебного заведения (Хоровое училище, СПбГК, ассистентура) — два поля «год начала» (необязательное) и «год выпуска». Колонки `*_start` в базе уже есть (`migration_person_card.sql`). Поле «Или другие годы учёбы» (`uPStudyStart/uPStudyEnd`) оставить для случаев вне этих трёх заведений. Везде, где годы выводятся (карточка в «Людях», страница человека, «Учились вместе»), показывать «1975–1980», если известно начало, иначе «выпуск 1980».
4. **Коллега**: поле «Должность, место работы» (`uPInstitution`) показывать для всех типов, для коллеги — с placeholder «например, концертмейстер класса Т.И.» и label «Должность, место работы». Для ученика — «Где работает сейчас / кем стал».
5. Те же три поля имени и годы начала — в форме «Предложить правку» (`person.html`) и в форме модератора (`moderation.html`); поиск людей (`app.js`, «Учились вместе», сопоставление своей карточки) — по `full_name`, как раньше.
Критерий: добавить человека «Иванов Иван Иванович, Хоровое училище 1975–1982» → в «Людях» карточка «Иванов Иван Иванович · выпуск 1982 · Хоровое училище», на странице человека «1975–1982». Старые записи отображаются без изменений.

## W3. Автор может удалить свой черновик статьи
1. Миграция (в тот же `migration_wiki_v5.sql`): политика `articles: автор удаляет свой черновик` — `for delete using (created_by = auth.uid() and status = 'draft')`. Отклонённые (`rejected`) тоже можно удалять автору. Подтверждённые и на проверке — нет.
2. `nasledie.html`, редактор (`#edit/:id`): кнопка «Удалить черновик» (`.btn.text`, цвет `--error`, иконка `delete`) → подтверждение M3-диалогом «Удалить черновик «…»? Это нельзя отменить» → `delete` → snackbar «Черновик удалён» → возврат к списку. Если у статьи есть загруженные картинки в `article-images` — удалить и их (best effort, ошибку не показывать).
3. В секции «Моё» у черновика и отклонённого — та же кнопка в полоске метаданных.
Критерий: свой черновик удаляется; на чужой или подтверждённой статье кнопки нет; попытка удалить через консоль чужую статью возвращает 0 строк.

## W4. Роль администратора: назначать модераторов на сайте
1. Миграция: `profiles.is_admin boolean not null default false`. RPC `set_moderator(target uuid, flag boolean)` — `security definer`, проверяет `is_admin` у вызывающего, ставит `is_moderator`, себя снять не даёт. RPC `list_members()` — `security definer`, только для admin: возвращает `id, full_name, relation_type, study_end, is_moderator, is_admin, created_at` из `profiles` плюс `email` из `auth.users` (админу можно видеть почту — он и так владелец проекта; никому другому почту не отдавать). Прямые политики на `profiles` не расширять (сейчас профиль видит только владелец — оставить).
2. Владельца назначает администратором Claude одним SQL при применении миграции (`update public.profiles set is_admin = true, is_moderator = true where id = '…'`). В отчёте написать, что это нужно.
3. `moderation.html`: вкладка «Участники» (видна только `is_admin`; страница модерации в целом остаётся для модераторов): M3-таблица или список — имя, отношение к Т.И., почта, дата регистрации, переключатель `switch` «Модератор». Переключение → `rpc set_moderator` → snackbar. Поиск по имени сверху, если участников больше 20.
4. В `onLoggedIn` для админа показывать пункт «Участники» в меню пользователя.
Критерий: админ включает модератора участнику → у того после перезагрузки появляется иконка модерации и очередь; не-админ вкладку не видит, `rpc` возвращает ошибку.

## W5. Обратная связь: письма автору и модераторам (волна 1)
Канал — e-mail (почта у всех есть, она же логин; SMS дорого и хрупко — не делаем). Механизм без своего сервера: триггеры в Postgres → `pg_net` → HTTP-запрос к Resend API. Ключ Resend хранится в Supabase Vault, не в коде.
1. Миграция (`migration_wiki_v5.sql` или отдельный `migration_notifications.sql`): включить расширение `pg_net`; функция `notify_email(to_email text, subject text, html text)` — `security definer`, читает ключ из `vault.decrypted_secrets` по имени `resend_api_key`, делает `net.http_post` на `https://api.resend.com/emails` от `post@khitrova.org`. Ошибки отправки не должны ломать основную операцию (обернуть в `begin … exception when others then null; end`).
2. Триггеры:
   - `after insert` на `events`, `people`, `articles` (когда `status = 'unconfirmed'`) и на `revisions` (`status = 'pending'`) → письмо всем модераторам (`profiles.is_moderator` → `auth.users.email`): «Новая запись на проверку: <тип> «<название>» от <имя>. Открыть: https://khitrova.org/moderation.html» (домен — из `project-notes.md`; пока сайт на `khitrova.zhamsx.workers.dev`, ссылку вынести в одну SQL-константу/настройку, чтобы поменять в одном месте).
   - `after update of status` на трёх таблицах (`unconfirmed → confirmed | rejected`) и на `revisions` (`pending → applied | rejected`) → письмо автору: «Ваша запись «…» опубликована» или «…отклонена. Заметка модератора: …» со ссылкой на запись.
   - Одно письмо на событие, без дайджестов; для статей `draft → unconfirmed` считать «отправлено на проверку».
3. На сайте: в секции «Моё» («Наследие») и на карточках своих записей показывать статус и `moderator_note` (сейчас заметка модератора автору не видна) — это уже даёт обратную связь без почты.
4. Что нужно от владельца (написать в отчёте): создать API-ключ в Resend (только отправка) и передать Claude для `vault.create_secret`; подтвердить домен отправителя (уже подтверждён для SMTP).
Критерий: добавить событие от тестового пользователя → модератору приходит письмо в течение минуты; подтвердить → автору приходит письмо; отправка не ломается, если ключа нет (запись всё равно создаётся).

- Не добавлять сборщики, фреймворки, npm. Библиотеки — только `<script src>` с CDN и закреплённой версией.
- Все строки по-русски, на «вы». Названия кнопок — глаголами.
- Перед началом `git pull`; перед коммитом `git status`, только свои файлы; сообщение по-русски («W1: вход — код из 6 цифр, Enter отправляет форму»).

- Если задание противоречит коду или невозможно — остановиться и написать вопрос в отчёте, не изобретать обход.
